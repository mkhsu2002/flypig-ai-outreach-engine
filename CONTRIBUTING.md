# Contributing

Thank you for helping improve FlyPig AI Outreach Engine.

Contributions are welcome in areas such as:

1. Documentation clarity
2. Generic prospect-research workflow improvements
3. Deduplication and identity-resolution guidance
4. Discovery Diversity patterns
5. Evidence and source-quality guidance
6. Qualification and Prospect Audit improvements
7. Tracker / handoff / schema improvements
8. Cross-model conformance testing
9. Validation and evaluation utilities
10. Fictional examples and privacy-safe test cases
11. Optional integrations that improve research quality or state continuity

## Before contributing

Please keep the public Core principles intact:

1. One canonical Tracker per campaign
2. Dedup before canonical prospect insertion
3. Discovery does not equal qualification
4. Research public facts before asking the user when possible
5. Separate verified facts, hypotheses, unknowns, and contradictory evidence
6. Require supportable evidence for material business-role and fit decisions
7. Challenge premature discovery convergence when materially different routes are plausible
8. Every QUALIFIED prospect receives skeptical Prospect Audit
9. Preserve SECONDARY / HOLD / PASS research history
10. Keep commercial fit separate from contact-route suitability
11. Never guess private contact data
12. Version the mission when evidence materially changes the target model
13. Use explicit stop conditions rather than searching indefinitely
14. Keep the public Core independent of a proprietary runtime or multi-agent requirement

## Public boundary

The Open Core ends at the Qualified Prospect Tracker.

Do not introduce mandatory public dependencies on:

```text
Message drafting
Email sending
Mailbox monitoring
Reply automation
Follow-up execution
A proprietary FlyPig runtime
A mandatory multi-agent framework
```

Proposals that touch downstream Controlled Outreach should be clearly separated from the public research Core.

## Never submit

Do not commit or post:

1. Real private customer prospect lists
2. Private email addresses or unnecessary personal data
3. API keys, tokens, passwords, or credentials
4. Confidential campaign files
5. Customer contracts
6. Private commercial evaluation sets or Knowledge Packs without explicit approval
7. Unmasked private verification audits intended to remain outside the public repository
8. Content copied from private deployments without permission

Real current public business information may be used in deliberate validation/control cases when privacy and research-purpose boundaries are clear.

## Contribution process

1. Open an issue for substantial changes.
2. Explain the problem and expected behavior.
3. Keep changes focused.
4. Add or update documentation when behavior changes.
5. Add a regression or conformance case when changing a mandatory process rule.
6. Use fictional examples by default; use real public data only for deliberate privacy-reviewed validation.
7. Confirm that no secret, customer-confidential, or unnecessary private prospect data is included.
8. Submit a pull request describing the change and its effect on the workflow.
